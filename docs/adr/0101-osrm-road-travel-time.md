# ADR-0101：車の移動時間を OSRM の道路の所要から取り、駐車・混雑の補正を足す

- 日付：2026-11-04
- 状態：採用
- 関連：ADR-0016・0018・0093・0096

## 背景
移動時間は直線距離×1.3÷手段の平均速度（車 25km/h。`domain/geo` の `estimateLeg`）で見積もっている。デモの仙台市の8区間で OSRM（OpenStreetMap の道路・車）の経路と比べると、道のりの誤差は平均 16%（−36〜+15%）だった。広瀬川を渡って八木山へ上る区間は短く出て（−36%）、幹線を一直線に行く区間は長く出る（+15%）。緯度差と経度差の円弧を足す式も試したが、平均 13% で大きな差は無く、坂・川・近距離の回り道はどちらの式でも拾えない。
一方、OSRM の所要は渋滞・信号待ち・駐車を含まない（平均速度 約35km/h）。そのまま使うと移動が短く出て、遅刻する計画になる。

## 選択肢
1. 案1：今のまま（直線距離×1.3）。係数だけ見直す
2. 案2：緯度差＋経度差の円弧（碁盤目の道を前提にした式）
3. 案3：OSRM の公開サーバーの Table API で地点 × 地点の所要と道のりを取り、端末に保存する。補正は a ＋ b × 所要
4. 案4：Google Maps の Routes API（渋滞込み）
5. 案5：OSRM を自前のサーバーで動かす

補正の形：係数を掛けるだけ（短い区間の駐車・徒歩が足りない）、分を足すだけ（長い区間の渋滞が足りない）、両方（a ＋ b × 所要）、時間帯ごとに変える（移動の行列が時刻ごとに要る大きな改修）を比べた。

## 決定
案3 を採り、補正は a ＋ b × 所要（駐車・玄関までの分 ＋ 混雑係数 × 道路の所要）。
- 取るのは、登録の案内の③と管理者設定の「道路の移動時間（車）」のカードにある「移動時間の見積もり方」（`components/RoadTravelChoice`）で「道路に沿った道のりから取る」を選び、［道路の移動時間を取る］（取ったあとは［取り直す］）を押したときだけ。選んだときに「押したときに、自宅と訪問先の緯度・経度だけを OSRM へ送って取ります。名前・住所は送りません」と目安（地点数・問い合わせの回数・かかる時間）を出す。既定は「直線距離から見積もる（外部へ送りません）」。直線距離に戻すと表を消す。送るのは位置のある〈スタッフ〉の自宅と〈利用者さん〉の場所（移動時間を手で決めた人を除く）の緯度・経度だけで、名前・住所は送らない。通信は `lib/roadTable` の1か所
- Table API（`/table/v1/driving/…?sources=…&destinations=…&annotations=duration,distance`）。公開サーバーの1回の上限は 100 地点（101 で TooBig を確かめた。100 地点で約1.1秒）。100 地点までは1回で全組、超えたら 50 地点ずつの区画（出発 × 到着）に分けて 1.1 秒あけて順に送る（公開サーバーは1秒に1回まで）。500 地点で 100 回・約4分の目安（150 地点で 9 回・12 秒だった）。表に入れる地点は 500 まで
- 保存は地点ごとに所要の近い順 50 件（`ROAD_NEAR_K`）だけ。全組（500 地点で 25 万組・約3MB）は localStorage に入りきらないため。出発の区画ごとに全部の行き先を取り終えたら絞る。150 地点で約 100KB、500 地点で約 300KB の見込み。残さなかった遠い組・道の無い組は直線距離から見積もる（遠い組はもともと続けて回る組に選ばれにくい）
- 契約：`DemoData.roads`（任意。`at`・`points`・`near`（地点ごとの行き先の番号）・`seconds`・`meters`（`near` と同じ並び）。所要は秒の整数、道のりは 10 m 単位）と `Org.roadTravel`（`parkMinutes` 0〜60 の整数・`trafficFactor` 1〜3）。無い古いデータは表なし・既定（保存データの版は変えない）。Excel のブックには入れない（読み込んでも今の値のまま）
- 既定は安全側（遅刻を避ける）：駐車・玄関まで 5分、混雑係数 1.5。デモの8区間では、市役所→泉図書館（幹線）を除き、今の見積もり以上になる
- 移動の行列（`matching/travel`）：車の区間で、表に両端の地点（緯度・経度の小数5桁で引く）と道があれば、移動＝ a ＋ b × 所要（分）・距離＝道のり（交通費に入る）。表が無い・地点が無い・道が無い・車でない（自転車・徒歩・公共交通）区間は今までどおり直線距離から。手で決めた移動時間（ADR-0096）・位置が未登録（ADR-0093）・同じ地点は今までどおり先に決まる
- 日ごと・AI で組むときに取る案は、組む前後に通信が要り、取らない区間との物差しのずれ（補正の有無）で選ばれる区間が偏るため捨てた。全組を一度に取っても 500 地点で約4分で、取り直すまで通信が要らない
- 表に無い地点（あとで足した・動かした）は直線距離から見積もり、カードに「表に無い地点が N あります」と出す。自動では取り直さない
- 帰属表示「経路：© OpenStreetMap contributors・OSRM」をカードに出す

## 理由とトレードオフ
- 得るもの：川・坂・一方通行を含む道のりで移動と交通費を見積もれる。キー・費用が要らない。取ったあとは通信なしで計算でき、計算は今までどおり同期・再現できる（表はデータの一部）
- 失うもの：外部送信の先が1つ増える（押したときだけ・緯度経度だけ）。公開サーバーはデモ用の扱いで、止まっても保証は無く、本番の運用には向かない。所要は渋滞・時間帯を表せず、補正は事業所で1組（場所・時間帯で変えられない）。自転車・徒歩・公共交通は対象外。保存データが増える（500 地点で約 300KB）。遠い組は道路の所要を使わない
- 捨てた案：案1・案2 は坂・川の回り道を拾えない（比較で平均 13〜16% の誤差）。案4 はキーと費用が要り、公開リポジトリにキーを置けない。案5 はサーバーの費用と保守が要り、静的サイトだけで動かす前提（design.md §1）から外れる。時間帯ごとの補正は、移動の行列を時刻ごとに持つ改修が要るため、効果を見てから決める
- ADR-0096 で捨てた「経路検索の API」は、毎回送ることとキー・費用を理由にしていた。この決定は押したときだけ送り、キー・費用が無いので、その理由に当たらない
