# ADR-0008：プリセットを利用者が編集できるデータにする

- 日付：2026-10-13
- 状態：採用（開いた日の自動作成は ADR-0053・0054 で提案を出す形に置き換わり、記録は持たない）
- 関連：PRD D20・D24・D25、ADR-0002・0010

## 背景
条件のプリセット（初期3種）を定数で持つと、利用者は自分の事業所に合わせて名前・重みを変えられない。プリセットごとの案を並べて比べるとき、条件ごとにどれだけ守れたか（希望 18/20件 など）も件数で見たい。

## 選択肢
1. プリセットの置き場所
   - A：定数のまま（編集できない）
   - B：データ（`DemoData.presets`）に持たせ、store が持ち主になる。初期値は seed の3種
   - C：localStorage の別のキーに持つ（データ一式の外）
2. 達成の件数
   - A：条件（Rule）ごとに「その条件の判定がある訪問」を分母、「その条件の判定をすべて満たした訪問」を分子にする（相性は ◎・○・△・× の件数）
   - B：条件1つずつの達成/違反の数のまま

## 決定
1-B、2-A。

- 形：`DemoData.presets: Preset[]`。`Preset`＝`{ id, name（1〜20字）, note（0〜60字）, weights: 条件の型 → { weight, hard } }`
- 数は最大6つ（初期の3つ＋利用者が足す3つ）。最後の1つは消せない。「初期値に戻す」で初期の3種（id：`standard`・`travel`・`people`）に戻す
- `repair` が直すもの：id の重複（最初の1件）、6つを超える分（後ろを捨てる）、0件（初期の3種）、重み（0〜5 に収め 0.5 刻みに丸める。数でなければ 0）、必須にできない型の必須（外す）。重みの範囲は zod では止めず repair で直す（手で直した JSON でデータ全体が読めなくならないように）
- プリセットは「重みを写して保存」で足せる。同じ型の条件が複数あるときは型ごとの最初の条件の重みだけを残す（プリセットは型ごとの重みなので）
- 達成の件数（evaluate の `achievements`）：相性は理由の `level`（2・1・−1・−2）で ◎・○・△・× を数える。重み0の条件は判定しないので出ない

## 理由とトレードオフ
- 得るもの：事業所ごとの考え方をプリセットとして残せる。データ一式（JSON・Excel）に入るので、ほかの端末・人へ渡せる。件数で見ると「希望を2件落とした」のように重みを変えた効果を言い直せる
- 失うもの：
  - 点数は、プリセットを作ったときの条件の点とは一致しない（比べられることを優先。ADR-0005・0010）
  - 同じ型の条件が複数あるときの保存は情報が落ちる
- 見直す条件：プリセットを6つより多く使いたい声が出たとき

## 影響
- contracts の `rules.ts` に `Preset`、store が `presets` を持つ。seed は初期値 `INITIAL_PRESETS` と `applyPreset` を持つ
- Excel のブックに「プリセット」シート（ADR-0006）
- 画面は条件の重みの画面のプリセットの節と、日の予定の「AI で組む」のプリセットで試す
