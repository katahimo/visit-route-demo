# ADR-0053：担当は訪問に持ち、AI は提案だけ、確定は伝えた内容、繰り返しの回は見るときに計算する

- 日付：2026-10-22
- 状態：採用（AI を使う入口と標準の担当は ADR-0062・ADR-0063・ADR-0064）
- 関連：PRD D314〜D325、ADR-0004（AI案を土台に手直し・ピン）・ADR-0010（点数の基準のプリセット）・ADR-0011（欠勤の振り直し）・ADR-0012（繰り返し）・ADR-0035（点数の基準）・ADR-0042（月まとめを画面の外で）・ADR-0051（訪問の詳細の欄）

## 背景
- 訪問に関わる状態が5つの層に分かれていた：定期パターン → 展開して保存した訪問 → 今の案と記録 → 確定した割当。さらに手直しの記憶・この日だけ試す重み・条件の変更の控えがあり、日の状態は6つあって、利用者が覚える言葉が多かった
- 決定：①確定＝〈スタッフ〉に伝えた内容（あとの変更は「未連絡の変更」として連絡の一覧に出す）②プリセットは残し、AI の実行と比較はその場だけ（保存しない）③繰り返しの回は見るときに計算し、変えた回だけ保存する ④スマホは見る・取り消す・担当を替えるまで
- デモなので古いデータは移さない

## 選択肢
1. 案A：今の層のまま言葉だけ減らす
2. 案B：担当を訪問に持ち、AI は提案（差）を出して利用者が反映する。確定は伝えた内容の写し、繰り返しの回は見るときに計算
3. 案C：案B に加えて、前の版のデータを移す。デモで移行の作りが重いので採らない

## 決定
案B。

### データの形（`src/contracts/`）
- `Visit` に `staffId`（担当。null＝担当なし）・`start`（組んだ開始。null は開始（早）で並べる）・`pinned`（AI で組み直しても担当を変えない）。`pattern.edited` は時刻・日付・所要・種類・メモを変えた回（担当・開始・ピンだけの違いは edited にしない）
- `DemoData` に `snapshots`（date → 伝えた内容。`ToldVisit = { id, clientId, staffId, start }`）と `reassigns`（date → 当てた欠勤の振り直しの情報。振り直す前の担当 `baseRoutes` など）を持つ。AI の案・記録・確定した割当・手直しの記憶は持たない
- `Pattern.usualStaffId`（繰り返しの担当）を1つ。〈利用者さん〉は担当を持たない
- `data.rules` の重み・必須は store の repair がいつも点数の基準のプリセットにそろえる（この日だけ試す重みは無い）
- 前の版のデータ・JSON は移さず、知らせて初期データで始める（`isOutdated`・`OUTDATED_MESSAGE`）

### 繰り返し（`src/patterns/`）
- `visitsOn`・`visitsIn`：保存した訪問と、利用中の〈利用者さん〉の繰り返しの計算した回（ID `${日}_${パターンID}`。同じ ID の保存した回があれば出さない）を開始の順に返す。計算した回の担当は繰り返しの担当。`putVisits` は計算した回を書くとき保存した回にする
- `splitPattern`：分けた日以降の、この回だけ変えていない保存した回は消し（新しい繰り返しで計算し直す）、変えた回は新しい繰り返しの回として ID を付け直す。`removePattern`：開始が今日より前の繰り返しは昨日で終わらせて残し（過去の予定を消さない）、今日以降の変えていない保存した回は消し、変えた回は単発にする
- 〈利用者さん〉を終了にすると、続いている繰り返しを昨日で終わらせる。終わった繰り返しは利用中でない人でも過去の回を計算する
- 繰り返しの回の ID が変わる操作（分ける・最終勤務日での受け持ちの移し）のあとは、伝えた内容の ID が今に無ければ同じ〈利用者さん〉・同じ元の日の回に読み替えて比べる

### 日の割当と確定（`src/lib/dayPlan.ts`・`confirmDay.ts`）
- 日の割当＝その日の計算に入れる訪問を担当ごとに開始の順に並べたもの。担当なしは別に持つ。`writeRoutes` が担当と開始を訪問に書く（変わる回だけ。計算した回は保存した回になる）。提案の反映・ドラッグ・「担当を変える ▾」・振り直しはこれを使う
- 訪問ごとの検査 `visitIssues`：担当なし・担当が休み・条件に合わない・時間に間に合わない。日の要対応はこの数。重みだけを変えても要対応にならない
- 確定：`tellDay` が今の担当・開始を `snapshots` に書く。`toldChanges`（伝えた内容と今の差＝連絡の一覧）・`toldStateOf`（`none`・`told`・`changed`）。伝えた日の訪問を全部取り消しても、伝えた訪問は「外れる」の未連絡の変更になる
- 日の状態は まだ伝えていない／確定済み／未連絡の変更あり の3つ。月の要対応は要対応・未連絡の変更・拘束時間超過の3種

### 画面の決まり
- 日の予定：担当・手直し・ピン・「確定（伝えた）」（未連絡の変更があれば「確定し直す（伝えた）」）を1画面で扱う。開いた日に自動で作らない（案の無い日は無く、担当なしの訪問が要対応で見える）。連絡の一覧の帯
- AI は提案を出すだけで、利用者が［反映する］まで訪問は変わらない。入口は「予定を組む」の担当を組む（ADR-0063）。提案の比較（`#/compare`）は欠勤前・今の担当・その場で作った提案で、保存しない
- 欠勤・キャンセルの欄：振り直しは `writeRoutes` で訪問に書き、`reassigns` に振り直す前の担当を残す。最後の段は「連絡・確定」で、「連絡したので確定」で伝えた内容を書いて閉じる
- 元に戻す：store の履歴（ADR-0054）。取り消し・反映・確定も1手
- 初期データ：繰り返しは前の月の1日から始め（過去の混み具合も見られる）、前の月の1日〜昨日は繰り返しの担当のまま「伝えた」状態にする（`withPastTold`）。今日からの日は AI で組まない（ADR-0064）。繰り返しの担当は、その〈利用者さん〉をよく担当した人から、繰り返しの曜日すべてに勤務があり同じ人の回が重ならない人を選ぶ
- Excel：訪問に担当・開始・ピン、繰り返しに担当。案・記録・確定した割当のシートは無い

## 理由とトレードオフ
- 得るもの：
  - 状態が「訪問ごと（担当あり／担当なし／要対応）」と「日ごと（まだ伝えていない／確定済み／未連絡の変更あり）」の2軸になり、覚える言葉が約10語に減る
  - どの画面も同じ訪問を読む。人の画面のカレンダー・週・月・ホームの数が同じ関数から出る
  - 「確定」が現場の意味（伝えた）になり、あとの変更を連絡の一覧で漏れなく伝えられる
  - 繰り返しの回を保存しないので、先の週・月もすぐ見え、データが小さい
- 手を入れた決まり：
  - 訪問の日付を動かしても担当は残す。新しい日で担当が休みなら要対応で分かる
  - メモの変更も「この回だけ変えた」に数える
  - 伝えた内容の1件には〈利用者さん〉も入れる（取り消した訪問の連絡の文に使う）
  - 「いつから変えますか」は今日以降。繰り返しを直す・消す・終わらせるとき、ピンの回も残す

## やめたもの
- AI の実行の記録（1日20件）と記録どうしの比較・「AI が出したままに戻す」・日の予定を開いたときの自動作成・「未作成」と展開の日数の管理・前の同じ曜日からのコピー：提案はその場だけにして層を減らすため
- この日だけ試す重み・「条件が変わった」の判定と作り直しの帯：重みは1組にし、条件を変えても今の担当は変わらず、訪問ごとの検査で要対応が出る
- 手直しの記憶（手で選んだ担当を同じ曜日・同じ時間の次の案でも固定し、確認の帯・来週分のまとめ変更・印を持つ仕組み）：「相性の学習」はしない方針と紛らわしく、状態の層も増える。代わりは繰り返しの担当を直す（これ以降・すべて）と、標準の週（ADR-0062）
- 条件の変更の控えと戻す（変更内容の一覧・項目ごとの戻す。DemoData の外に控えを持つ仕組み）：「条件が変わった」の判定ごと無くなり、控えは容量と整合の負担が大きい。戻すは全体の元に戻す（ADR-0054）で足りる
- 「欠勤あり（対応済み）」の表示：訪問の無い人の欠勤は要対応にならないので不要
