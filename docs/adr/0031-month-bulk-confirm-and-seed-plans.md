# ADR-0031：月の「問題の無い日をまとめて確定」と、確定後の「次の確定していない日へ」

- 日付：2026-10-19
- 状態：採用（確定は「〈スタッフ〉に伝えた内容」。ADR-0053）
- 関連：PRD D223・D224、ADR-0025（ホーム・進み具合の帯）、ADR-0026（独自の確認）、ADR-0053

## 背景
確定は日の予定の「確定（伝えた）」だけで、一月を確定するには日ごとに「日を開く → 確定 → 確認 → 戻る」を約22日ぶん繰り返す必要があった（約90回の操作）。ホームの「確定していない日 N日」も月の画面へ移るだけだった。

制約：データを書くのは store の `update(fn)` だけ。契約に項目を足さない。「確定」の意味（ADR-0053）は変えない。日の状態は `useDayStatuses` の1か所で数え、月・ホーム・帯で同じ。

## 選択肢
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| まとめて確定A：要対応に1つも出ない日だけ（条件が変わった・拘束超・欠勤も外す） | 要対応に出ている日を黙って確定しない（月の要対応と同じ判定） | 振り直し済みの欠勤の日・拘束の注意だけの日は日の予定で確定する | 採用 |
| まとめて確定B：入らない訪問・必須の違反・休みの人に残る訪問が0の日 | 手数が最も減る | 条件が変わった日・拘束超・欠勤の日も黙って確定する | 不採用 |
| まとめて確定C：案のある日をすべて確定 | 単純 | 入らない訪問がある案を確定してしまう | 不採用 |
| まとめて確定D：今日より前の日も含める | 日の予定と同じ範囲 | 「確定していない日」の一覧（今日以降）と数が食い違う | 不採用 |
| 前に伝えた内容が変わった日も含めて置き換える | 日の予定の確定と同じ範囲 | 〈スタッフ〉に伝えた予定を差を見ずに置き換える | 不採用 |
| 次の日へA：確定済みの印の横にボタン | 状態で決まり、読み直しても出る | 見出しが少し混む | 採用 |
| 次の日へB：確定の知らせ（トースト）に操作を付ける | 確定の直後だけ | トーストは短く消える文だけの部品で、キーボードで届かない | 不採用 |

## 決定
1. 問題の無い日をまとめて確定（月の右の欄の「確定していない日」）：今日以降のまだ伝えていない日のうち、要対応（要対応の訪問がある日・拘束超。PRD D321）に出ない日を、独自の確認のあと1回の `update` で確定する。書き方は日の予定の確定と同じ純粋関数 `lib/confirmDay` の `confirmDay`。日の状態は `useDayStatuses`、要対応は `attentionList` のものを使い数え直さない
   - 確認には確定する日付と、残す日（問題のある日は日付も、未連絡の変更のある日は日数）を出す。0日なら押せず理由を見せる
   - 前に伝えた内容から変わった日は対象にしない。日の予定で連絡の一覧を見て確定し直す
   - 対象は右の欄の一覧と同じ今日以降
   - 主ボタンにしない（月の主ボタンは進み具合の帯の次の一手）
2. 次の確定していない日へ：日の予定で確定済みのとき、見出しの印の横に「次の確定していない日へ（M/D）」を置く。その日より後・今日以降で、月・ホームと同じ数え方の確定していない日の最初。無ければ出さない

## 理由とトレードオフ
- 得るもの：一月の確定が約90回の操作から確認を含む2回に。「確定」の書き方が1か所（`confirmDay`）になる
- 失うもの：まとめて確定は1日ずつ案を見ずに確定する（一度も確定していない問題の無い日に限り、確認に日付を出して補う）。要対応に出る日・変更のある日は日の予定で1日ずつ確定する
- 見直す条件：「拘束の注意・欠勤の日もまとめて確定したい」という声が多ければ、見るだけの要対応を対象に戻すか選べるようにする
