# 実装の原則（Clean Code / SOLID をコードの縮尺で）

`principles.md` は境界（コンポーネント・サービス）の縮尺。ここは **1ファイル・1関数・1部品** の縮尺で、AI エージェントが実装・レビューするときの決まり。
目的は同じ：**変更の影響を小さい範囲に閉じ込め、AI が1回で読み切れる大きさに保つ。**

## 1. 測れる決まり（`scripts/check_code.py` が検査する）

| 決まり | 既定の上限 | 原則 | 超えたときの直し方 |
|---|---|---|---|
| 1ファイルの行数 | 600 行 | SRP | 変わる理由ごとにファイルを分ける（計算・状態・見た目） |
| トップレベルの関数・部品の行数 | 150 行 | SRP | 下の「分け方の型」で切り出す |
| 層の依存 | 設定の `layers` | DIP・依存の向き | 型・純粋関数を下の層へ移す。上の層のものは引数で受け取る |
| 循環 import | 0 | 依存の向き | 両方が使う部品を3つ目のファイルへ出す |
| 使われない export | 0 | Clean Code（死んだコード） | 消す。ファイルの中だけで使うなら export を外す |

- 今ある違反は基準（baseline）に入れ、**新しい違反を増やさない**（ラチェット）。直して減ったら基準を縮める
- Biome を使うプロジェクトでは `--sync-biome` で同じ決まりを `biome.json` に書き出す（層の違反は lint のエラー、長い関数は警告）。決まりの正は `code-rules.json` の1つだけ
- 上限は目安。超えるのが正しい場面（表のデータ・1つの長い switch で網羅したい）は、基準に入れて理由をコミットに書く

## 2. 層と依存の向き（フロントエンドの最小形）

内側ほど変わりにくく、外側ほど変わりやすい。**依存は内側へだけ向ける。**

```
contracts（型・契約）  ←  domain / 計算の層（純粋関数）  ←  lib（画面のための純粋関数）
      ←  store（データの持ち主・保存）  ←  hooks（React と store をつなぐ）  ←  components  ←  pages / app
```

- 純粋関数の層（domain・計算・lib）は React・store・DOM・画面を import しない。テストは入力と出力だけで書ける
- React のフック（`use*`）は hooks か components に置き、lib に混ぜない
- データを書き換えるのは store だけ。画面は「新しいデータを返す純粋関数」を作り、store の更新関数に渡す
- 契約（型）は実装に依存しない。実装が使う定数・検査を契約に置きたいときは、契約の側へ移す

## 3. SOLID をコードで見る

| 原則 | コードでの兆候 | 直し方 |
|---|---|---|
| S 単一責任 | 1部品に状態が10個以上・effect が5個以上・「〜と〜と〜」で説明する部品／計算と描画が同じ関数 | 計算は純粋関数へ、状態と処理はカスタムフックへ、見た目は小さい部品へ |
| O 開放閉鎖 | 種類（条件の型・繰り返し方など）が増えるたびに、離れた複数の switch / if を直す | 種類ごとの違いを1つの表（`Record<種類, {…}>`）か1つの関数に集める。switch の `default` は `const _: never = x` で網羅を型で確かめる（黙って無視しない） |
| L 置換 | 同じ形の props・関数なのに、特定の呼び出し側だけ別扱いが要る | 共通の部品の約束をそろえるか、別の部品に分ける |
| I 分離 | props が15個以上／対になった props（`picked`・`onPick`）が並ぶ／使う側の多くが一部しか使わない大きな型 | 関連する props を1つのオブジェクトにまとめる。読むだけの側と書く側で型・フックを分ける（`Pick<>` で絞る） |
| D 依存性逆転 | 純粋関数が Worker・時刻・乱数・保存を直接呼ぶ／モジュールの大域変数で状態を持つ | 依存を引数で受ける作る関数にする（`createX(solve)`）。テストで差し替えられる |

## 4. Clean Code の決まり

- **重複は2回目で疑い、3回目で共通化する**（Rule of Three）。共通化の前に既存の部品・関数を grep で探す（同じ働きの関数を新しく作らない）
- **名前は1つの意味に1つ。** 同じ名前で別の意味の関数を作らない（`unassignedDays` が配列を返すものと数を返すもの、など）。日付の書式・時刻の変換のような小さい関数は1か所に置く
- **マジックナンバーは名前を付けて1か所に。** 同じ値（時間軸の始まり・閾値・EPS）を複数のファイルで持たない
- **死んだコードは残さない。** 使われなくなった関数・部品・CSS は、その変更と同じコミットで消す。テストからだけ使う関数も消す（テストと一緒に）
- **コメントは「なぜ」。** 何をするかはコードと名前で表す。コメントと実装が食い違ったら、その場で直す
- **深いネストは早期 return で浅くする。** 3段を超えたら分ける

## 5. 分け方の型（React + TypeScript）

巨大な部品は次の順で小さくする。1回に1段ずつ、挙動を変えずに（テスト・e2e を通しながら）。

1. **計算を純粋関数へ。** `useMemo` の中身・イベントの中のデータの組み立てを `lib/` の関数にし、テストを付ける
2. **状態と処理をカスタムフックへ。** 関係する `useState`・`useEffect`・ハンドラーの塊を `useXxxFlow()` にまとめ、部品は戻り値だけを使う
3. **見た目を小さい部品へ。** 画面の区画（帯・欄・一覧）ごとに部品にし、props は「表示に要るもの」と「押したとき」だけ渡す
4. **同じ形の処理が2画面にあれば共通の関数・部品へ。**

## 6. やりすぎない

- 実装が1つしかないインターフェース・Factory・クラス階層は作らない。境界（他モジュール・外部・テストで差し替え）があるときだけ
- 分割で「本当の処理にたどり着くまで5ファイル以上」になったら戻す
- 小さい関数（数行）を無理に分けない。行数より「変わる理由の数」を見る
